## 2. UX practices worth copying

| ID | Practice | Evidence |
|---|---|---|
| U1 | One prompt per day or per week, not a feed. BeReal: one daily alert. Retro: weekly. Airbuds: Sunday recap. | C1, C3, C6 sources |
| U2 | Reciprocity gate: you see friends' items only after you share. BeReal made this the core. For this product: "approve or decline today's pick to see your friends' picks". A decline must count too, or the gate pressures people to share. | C1 |
| U3 | Home-screen widget as the main surface. Locket and Airbuds both grew on widgets. | C2, C6 |
| U4 | Invite gating gives fast chart rank and weak retention (Lapse needed 5 invites). Prefer "the app is empty without friends, so invite 1 to start". | C4 |
| U5 | Friend cap. Locket started with a small friend limit [mem]. CloudKit caps a share at 100 participants (see T-c). A cap of about 20-50 fits both. | T-c |
| U6 | Photo permission onboarding: explain the value before the system prompt. Ask in response to a user action, not at first launch (Apple guidance). Suppress the automatic limited-library prompt with the Info.plist key. | https://developer.apple.com/documentation/photokit/delivering-an-enhanced-privacy-experience-in-your-photos-app |
| U7 | No timeout auto-send (PicSee does it). It contradicts "only when you say yes". | C7 |
| U8 | Retention numbers: no public D1/D30 figures were found for BeReal, Locket, Retro, or Lapse. Only MAU/DAU claims exist. Locket 9M DAU vs 80-90M downloads suggests about 10% of installs active daily (company numbers). Airbuds 1.5M DAU / 5M MAU = 30% DAU/MAU. | C2, C6 |

## 3. Technical claims

### T-a. Background processing

| Claim | Verdict | Notes |
|---|---|---|
| `BGProcessingTaskRequest.requiresExternalPower` runs the task only on power | VERIFIED | Property exists since iOS 13: "requires a device connected to power". |
| Processing tasks run only when idle and can be cut short | VERIFIED | Docs: "Processing tasks run only when the device is idle. The system terminates any background processing tasks running when the user starts using the device." Use `expirationHandler`. Tasks "can run for minutes". There is no guarantee of when or how often a task runs. The system decides, usually overnight [mem]. Design for resumable batches with checkpoints. |
| `BGContinuedProcessingTask` exists (iOS 26) | VERIFIED | iOS/iPadOS 26+. It "starts in the foreground and can continue running in the background". The system shows progress in a Live Activity and the user can cancel it. It must report progress or it is terminated first. It is for a user-started job (for example "analyze my library now" at onboarding). It does not schedule nightly work. A GPU resource option exists [mem, UNCLEAR]. |

### T-b. Apple Reference Image

| Claim | Verdict | Notes |
|---|---|---|
| Apple Reference Image exists on iPhone 18 Pro | VERIFIED | Announced Sep 2026 for iPhone 18 Pro / Pro Max. Opt-in in Settings > Camera > Reference Image. The sensor signs pixel data at capture. 10-35 MB per capture. Main camera only (secondary source). Not in China at launch. EU capture not at launch. |
| The API is `PHReferenceImageInfo` / `imageContainsReferenceImageData` | VERIFIED, but iOS 27, not iOS 26 | Class `PHReferenceImageInfo`, iOS/iPadOS/macOS 27+. Initializers: `init(asset: PHAsset)`, `init(fileURL:)` (HEIC, JPEG, DNG). Its only property is `imageContainsReferenceImageData: Bool`. |

### T-c. CloudKit sharing (CKShare)

| Claim | Verdict | Notes |
|---|---|---|
| The app can create a CKShare | VERIFIED | Create `CKShare` for a record zone (zone-wide) or a root record (hierarchy). Save with `CKModifyRecordsOperation`. A record can be in only one share. Zone-wide sharing fits an unbounded "my posts" collection. The default zone cannot be shared or subscribed to. |
| The app can add/remove participants in code | VERIFIED | `CKFetchShareParticipantsOperation` turns an email or phone number into a participant. Then call `addParticipant(_:)` and save. `removeParticipant(_:)` + save removes a friend. `publicPermission` must be `.none` for an invite-only share. |
| Participants can be added silently, with no accept step | FALSE | The owner can add the participant record in code. The friend still must open the share URL. CloudKit checks that their iCloud account matches the participant details. Then the app calls `CKAcceptSharesOperation`. "A participant can't accept a private share unless the owner adds them first." You must deliver the URL yourself (Messages, email, AirDrop, QR, or your own channel). Without a server, Messages/QR/AirDrop is the only channel. |
| Limits | VERIFIED | Maximum 100 participants per share. "Limits can change". Each participant needs an active iCloud account. |
| Friend graph with no server | Feasible design, not verified in practice | Each user owns one custom zone ("my posts") shared with all their friends. A friendship = each user is a participant in the other's share. That gives two invite URLs per friendship, or one if the second is sent automatically after the first accept. iCloud storage of the poster counts against their quota [mem]. You cannot find friends by contact discovery (user discoverability was deprecated in iOS 17 [mem]). |

URLs: https://developer.apple.com/documentation/cloudkit/shared-records.md , https://developer.apple.com/documentation/cloudkit/ckfetchshareparticipantsoperation.md , https://developer.apple.com/documentation/cloudkit/ckshare/addparticipant(_:).md , https://developer.apple.com/documentation/cloudkit/ckerror/toomanyparticipants.md

### T-d. Push to friends via CloudKit subscriptions, no server

| Claim | Verdict | Notes |
|---|---|---|
| Subscriptions on the shared database notify friends of new posts | VERIFIED | Use `CKDatabaseSubscription` in each friend's shared database, created at first launch. It fires for changes in any custom zone in that database, which suits shared zones that are unknown in advance. Only private and shared databases support it. `CKQuerySubscription` is not supported in the shared database. |
| Visible alerts (not only silent) | UNCLEAR | `notificationInfo` allows alert fields in general. Apple's example uses silent push (`shouldSendContentAvailable`). Developers report setting `alertBody` on shared-DB database subscriptions, but no official confirmation and several "pushes not arriving" threads. Fallback: silent push, then a local notification. That fallback depends on iOS background launch budget and fails when the user force-quits the app [mem]. Test on real devices in Production. |
| Throttling | PARTIAL | Docs: "the system coalesces notifications, don't rely on them for specific changes". Payload may drop data. No CloudKit-specific number found. |
| Risk | | With no server you cannot shape the notification text per friend, schedule a daily "drop", or send a reliable alert. A minimal push relay (stateless, no photos) removes this risk. |

| Claim | Verdict | Notes |
|---|---|---|
| PHPicker needs no permission | VERIFIED | Runs out of process. But the user picks, which contradicts "AI picks". The app also gets no background access. |
| Limited access lets background analysis read the library | FALSE for the product goal | With limited access, the app "can only access these assets", the user-selected ones. Background fetches see only that selection. "AI picks from your life" needs full access (`.authorized` for `.readWrite`). |

## 5. Key risks for the owner's design

| ID | Risk |
|---|---|
| R1 | Reference Image cannot give a "verified" result to the app. Only "has reference data". It is iOS 27, Pro-only, opt-in. Do not market "verified photo" on it. Use "camera-original" heuristics and say "likely original". |
| R2 | The core value ("AI picks from your whole life") needs full photo library access. Many users refuse it. |
| R3 | No silent friend add in CloudKit. Every friendship needs an invite URL and an accept step, and both sides need iCloud. Max 100 per share. |
| R4 | Visible push on new posts without a server is UNCLEAR. A tiny stateless push relay (no photos) removes the risk and keeps the "no photo storage" goal. |
| R5 | Background scoring time is not guaranteed. Design for incremental scoring of new photos, plus an onboarding `BGContinuedProcessingTask` run. |
| R6 | Apple Photos Memories (C11) already does on-device curation for free. The product must win on the social loop and the nudge to go out, not on curation. |
| R7 | App Review: "user cannot pick a photo" is fine. Full library access needs a clear purpose string. Sign in with Apple only is fine. |
